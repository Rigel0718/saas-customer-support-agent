# Agent vs Workflow — 2차 Evaluation 결론

작성일: 2026-10-31 · OpenSpec Change `access-audit-environment`

**결론:** 정보량이 큰 접근 상실 진단에서도 두 방식의 정확도는 같았다. 차이는 비용, 지연, 장애 유형에서만 나타났다.

- **비용:** 노이즈 이벤트가 적으면(N=50) Workflow가 더 싸고 빨랐다. 많으면(N=5000) Agent가 약 43% 쌌다.
- **장애 유형:** Workflow는 단일 LLM 호출이 길어 요청 Timeout에 취약했다. Agent에는 원인 하나를 찾고 조사를 멈추는 완전성 위험이 남아 있었다.
- **Agent 자율성의 실제 내용:** Agent가 자율적으로 한 일은 대부분 "어제 이후, 요청자 대상, 특정 종류"라는 예측 가능한 필터 선택이었다. 그래서 이번 결과는 "Agent가 필요하다"보다 **"Workflow의 선조회 범위를 문의 조건으로 좁혀야 한다"**는 근거에 더 가깝다.

이 판단은 아래 네 Case, 두 노이즈 수준, 그리고 이번 두 구현에 한정한다.

## 1. 실험 질문과 범위

1차(`invite-50-v1`)는 조회 7회로 정보를 모두 미리 가져올 수 있는 환경이었다. 2차는 정보량이 커서 미리 다 가져오기 어려운 업무를 골랐다.

**질문:** 노이즈가 적을 때와 많을 때, 다음 두 방식의 정확도·비용·지연은 각각 어떻게 변하는가?
- Workflow: 전부 가져와서 한 번에 판단
- Agent: 필요한 것만 찾아서 조회

**Case:** 네 Case 모두 같은 문의를 사용한다. "어제까지 되던 멤버 관리 기능을 오늘부터 사용할 수 없습니다. 무엇이 바뀌었는지 확인해 주세요."

| Case | 상황 | 기대 진단 |
|---|---|---|
| A01 | 20시간 전 관리자 B가 요청자를 admin에서 member로 강등 | `role_demoted` |
| A02 | 22시간 전 결제 실패로 system이 구독을 past_due로 전환 | `subscription_past_due` |
| A03 | A01과 A02의 원인이 동시에 있음 | 두 원인 모두 |
| A04 | 관련 변경 없음. 5일 전 member에서 admin으로 승격된 이벤트만 있음(함정) | `needs_information` |

**노이즈 N:** 조직에 미리 넣어둔, 원인과 무관한 Audit Event 수다. 기준 시각 이전 30일에 분포하며 로그인, 문서 조회·수정, 초대, 다른 사용자의 역할 변경으로 구성된다. seed 7로 고정했다.

**두 모드의 조회 방식:**
- **Workflow:** 고정 9단계로 조회한 뒤 LLM을 1회 호출한다. 조회에는 Audit Event 14일치 최신 500건이 포함된다.
- **Agent:** 1차와 같은 Agent에 읽기 전용 Tool `get_audit_events`를 하나 추가했다. 한 번에 최대 50건을 조회하고, `total_count`와 `truncated`로 결과가 잘렸는지 알 수 있다. Prompt는 튜닝하지 않았다.

## 3. Correctness 기준

**GT:** `evaluation/data/access_gt.json`(access-gt-v1)이다. 실행 전에 확정했고, SHA-256을 manifest에 기록했다.

**판정 방식:** 1차와 달리 LLM Judge를 쓰지 않았다. 96건 전부에 대해 Claude가 Trace 근거를 붙여 라벨 초안을 만들고, 사용자(geonhee)가 그대로 확정했다. 사람 라벨이 곧 최종 판정이므로 Calibration 단계는 없다.

**판정 규칙(`labeling_rules`):**
- 멤버 관리를 막는 현재 조건(요청자 role=member 또는 구독 status=past_due)을 원인으로 명시해야 한다.
- 변경 시각이나 행위자를 생략한 것은 오답이 아니다.
- 관찰과 모순되는 주장은 오답이다. 존재하는 원인 이벤트를 "없다"고 단정하는 경우도 포함한다.
- 노이즈나 과거 이벤트를 맥락으로 언급하는 것은 괜찮다. 원인으로 주장하면 오답이다.

**비율 정의:** 1차와 같은 세 가지를 쓴다.
- Execution Success = 유효한 Diagnosis가 저장된 수 / 시작한 실행 수
- Correctness = correct / (correct + incorrect)
- 시작 실행 대비 정답 = correct / started

## 5. Timeout 민감도 해석

- **v1에서 Workflow가 실패한 원인은 진단 능력이 아니라 단일 호출의 지연이었다.** 요청 Timeout을 60초로 늘리자 Timeout 실패가 0건이 되었고, 진단이 나온 건은 모두 정답이었다.
- **단일 호출의 지연 꼬리는 구조적인 차이다.** v2에서 Workflow의 LLM 호출은 최대 36.4초 걸렸고, Agent의 호출은 최대 18.4초였다. 판단을 한 호출에 몰아넣으면 Timeout 정책에 더 민감하다.
- **실행 시점의 API 상태도 섞여 있다.** Agent의 평균 Latency는 v1 32.9초에서 v2 27.3초로 줄었다. v1의 Workflow 성공 수도 회차별로 4/8, 2/8, 6/8로 크게 달랐다. 그래서 v1의 실패율 50%를 구조 자체의 성질로 일반화하지 않는다.
- **운영 관점의 함의:** 1차에서 쓴 30초 요청 Timeout은 입력 1.7k tokens 수준의 Workflow에 맞춘 값이었다. 선조회 양이 늘어난 Workflow에는 맞지 않는다. Timeout은 모드별 호출 크기를 고려해 정해야 한다.

## 6. 실패 사례와 행동 분석

**Agent의 조기 종료(완전성 위험):** v1 #5(A03 N=50)에서 다음 순서로 조사했다.
1. 역할 강등 이벤트를 찾았다.
2. 행위자를 조회했다.
3. 구독은 조회하지 않고 종료해 `subscription_past_due`를 누락했다.

1차 C05에서 원인 하나를 찾은 뒤 `get_subscription`을 생략한 것과 같은 패턴이다. 빈도는 다음과 같다.

| 실행 | A03 Agent 실행 | 누락 |
|---|---:|---:|
| access-48-v1 + v2 | 12회(진단 완료 11회) | 1회 |
| 파일럿(access-16-v1, v2) | 4회 | 2회 |

빈도는 낮지만 사라지지 않았다.

**잘린 조회 결과에 대한 대응이 일관되지 않다.** Agent 48회 중 10회는 잘린 결과(`truncated=true`)를 받았다.
- 대부분 필터를 추가해 범위를 다시 좁혔다.
- v1/v2의 #26(A01 N=5000)은 강등 이벤트를 찾지 못한 채, 현재 role=member만으로 진단했다. "변경이 없었다"고 단정하지는 않아서 정답이다.
- 파일럿 `access-16-v2`의 같은 Case에서는 "역할 변경 이벤트가 발견되지 않았다"고 단정했다. GT 규칙대로라면 오답에 해당한다.

**Agent의 조회는 대부분 예측 가능했다.** Agent 48회 모두 Audit Event를 조회했다. 그중 46회는 조회 시작 시점을 "어제(10-29~10-30) 이후"로 잡았고, 29회는 대상(요청자)이나 이벤트 종류 필터를 썼다. 즉 자율적인 필터 선택은 문의 문구("어제까지")와 진단 대상에서 거의 기계적으로 도출되었다.

**두 모드 공통의 출력 오류:** v2의 `invalid_output` 3건은 모두 `invalid_policy_reference`였다. 정책 문서 ID를 `search_policy`가 아닌 관찰(사용자, 감사 로그 등)의 근거에 붙인 경우다. 모드 차이가 아니라 공통 출력 계약에서 생기는 거부다.

**A04 함정:**
- Workflow N=50은 5일 전 승격 이벤트를 실제로 보았지만, 원인으로 주장하지 않았다.
- Workflow N=5000은 이 이벤트가 최신 500건 밖이었다.
- Agent는 조회 범위를 1~2일로 잡아서 이 이벤트를 보지 않았다.

따라서 함정에 대한 Agent의 반응은 검증되지 않았다.

## 7. 2차 Design Decision

1. **정보량이 작으면 Workflow를 유지한다.** N=50에서 Workflow는 정확도가 같았고, 비용은 약 25% 싸고 Latency는 약 4초 짧았다.
2. **정보량이 크다고 바로 Agent로 바꾸지 않는다. 먼저 Workflow의 선조회 범위를 좁힌다.** N=5000에서 Agent가 싼 이유는 자율성 자체가 아니라 조회 범위를 좁혔기 때문이다. 그 필터는 문의 조건으로 미리 정할 수 있었다(6절). 고정 필터를 쓰는 Workflow가 같은 비용 이점을 얻을 수 있는지는 **아직 측정하지 않은 가설**이다.
3. **Complete Diagnosis가 중요한 업무에서는 Agent의 조기 종료 위험을 감수하지 않는다.** 1차와 같은 결론이다.
4. **운영 설정:** 선조회 양이 큰 Workflow에는 30초 요청 Timeout이 부족하다. 모드별 호출 크기에 맞춰 Timeout을 정한다.

**한 줄 요약:** 이번 업무는 노이즈가 많았지만, 조사 경로는 여전히 예측 가능했다. Agent의 자율성이 실질적인 가치를 내려면, 조사 경로가 관찰에 따라 실제로 갈라지는 업무가 필요하다. 이번 Case에서는 아직 그런 상황이 나오지 않았다.

## 8. 한계

- **표본:** Case 4개, 노이즈 수준 2개, 반복 3회다. 통계적 유의성을 주장하지 않는다. 정확도는 두 모드 모두 천장에 가까워 차이를 판별할 힘이 작다.
- **판정:** 사람 라벨은 Claude가 초안을 만들고 사용자 1명이 확정했다. 독립적인 다중 평가자 검증은 없다.
- **Case 설계:**
  - A01과 A02는 현재 상태만으로도 원인을 알 수 있어서, Audit Log가 필수 정보가 아니었다.
  - 인과 체인 깊이를 변수로 두지 않았다.
- **조건 혼재:** v1과 v2는 Timeout뿐 아니라 실행 시점의 API 상태도 달랐다.
- **비교 가능성:** 1차(`invite-50-v1`)와는 Tool 목록, Workflow 단계, 정책 문서가 다르다. 두 결과를 직접 합산하거나 비교하지 않는다.
- **비용 집계:** 완료된 실행만 평균했다. Timeout으로 실패한 호출의 비용은 기록되지 않았다.

## 9. 후속 후보

이번 작업에서 구현하거나 성능을 주장하지 않는다.

- **Filtered Upfront Workflow:** 문의 기준 시각 1~2일 이내의 요청자 대상 이벤트와 구독 상태 변경 이벤트만 선조회하는 Workflow. 비용 이점이 Agent의 자율성에서 왔는지, 단순히 조회 범위 축소에서 왔는지 분리할 수 있다.
- **Audit Log 없이는 풀 수 없는 Case:** 현재 상태에 원인이 드러나지 않는 Case. 예: 이미 복구된 변경의 영향, 다른 사용자의 변경이 연쇄적으로 영향을 준 경우.
- **조사 경로가 관찰에 따라 갈라지는 업무 탐색:** Agent의 자율성이 필요한 조건을 찾는 다음 질문이다.
- **공통 출력 계약 개선:** `invalid_policy_reference`를 줄이는 방향. 정책 근거를 trace와 분리하는 방안 등.
