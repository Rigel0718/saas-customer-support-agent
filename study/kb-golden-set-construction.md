# Golden Set 구축 방법: Support Knowledge Base 사례

작성일: 2026-11-02. 대상: `.evaluation-results/kb-cases-v1/cases.json` (Langfuse 공개 Discussion 기반, 29건 · 채점 주장 35개).

이 문서는 이번 프로젝트에서 Golden Set을 만든 기준과 절차를 실제 사례로 정리한 학습 노트다. 일반 원칙 → 이번에 실제로 한 일 → 실제로 발견한 문제 순서로 적는다. **아직 이 Golden Set으로 Agent·Workflow 실험은 실행하지 않았다.** 아래 내용은 평가 결과가 아니라 평가 데이터를 만든 과정이다.

## 1. 한눈에 보기

| 단계 | 핵심 질문 | 이번 사례 |
|---|---|---|
| 1. 출처 선택 | 정답의 권위는 어디서 오는가 | 공개 Discussion 중 **메인테이너(MEMBER)가 답한** 스레드 227건 |
| 2. 시점 고정 | 질문자가 그 시점에 알 수 있던 정보는 무엇인가 | 질문 작성 시각을 `as_of`로 두고, 그 이전 문서·스레드만 보이게 함 |
| 3. 표본 추출 | 내가 고른 쉬운 문제만 들어가지 않았나 | `random.Random(11)`로 섞은 순서대로 검토, 적격 30건에서 중단 |
| 4. 적격 판정 | 이 문제는 정답을 낼 수 있는 문제인가 | 질문 시점 지식 베이스에 정답 근거가 있어야 적격. 55건 검토 중 26건 제외 |
| 5. 주장 분해 | 정답의 어느 부분을 채점하는가 | 답변을 채점 주장(claim)으로 쪼개고, 근거 없는 부분은 `unscored_parts`로 분리 |
| 6. 근거 연결·점검 | 근거가 정말 그 시점에 존재했나 | 서비스 함수로 30건 전체 재조회 → 오류 3곳 수정 |
| 7. 채점 설계 | 무엇을 정답으로 인정하는가 | 1층 정답 여부(내용) + 2층 근거 지표(자동) |
| 8. 사람 검토 | 초안 작성자의 오류를 누가 잡는가 | Claude가 초안, 사용자가 검토·확정. 미검토 Case 8건 추가 검토 → 1건 제외, 1건 수정 |

최종: **227 후보 → 55 검토 → 29 확정(주장 35개)**, 제외 26건은 사유와 함께 기록.

## 2. 왜 이런 Golden Set이 필요했나

평가 목표는 "고정 RAG Workflow와 Agentic RAG 중 무엇이 지원 문의에 더 나은가"다. 이걸 비교하려면 다음 세 조건을 만족하는 문제가 필요하다.

1. **정답이 있다.** 정답이 모호하면 두 시스템의 차이가 채점 잡음에 묻힌다.
2. **풀 수 있다.** 지식 베이스에 근거가 없는 문제는 둘 다 틀린다. 비교 정보가 없다.
3. **현실적이다.** 직접 만든 가상 문의는 만드는 사람이 정답을 알고 쓰기 때문에 쉬워진다. 그래서 1·2차 평가의 가상 SaaS 데이터 대신 실제 공개 지원 데이터로 전환했다.

## 3. 단계별 기준과 사례

### 3.1 출처 선택: 정답의 권위

- **기준:** 정답은 "그럴듯한 답"이 아니라 그 제품을 책임지는 사람이 실제로 준 답이어야 한다.
- **이번 사례:** GitHub Discussion 중 작성자 소속이 `MEMBER`인 답변만 후보로 삼았다. 기간은 스냅샷 범위 `[2025-07-01, 2026-10-19]`.
- **주의:** 메인테이너 답변도 틀리거나 이후 바뀔 수 있다. 그래서 "답변 = 정답"이 아니라 "답변 중 질문 시점 문서로 뒷받침되는 주장 = 정답"으로 좁혔다(3.4).

### 3.2 시점 고정(as_of): 데이터 누출 방지

Golden Set에서 가장 쉽게 놓치는 문제다. 오늘 기준 문서로 작년 질문을 풀면, 질문 이후 추가된 기능 설명이나 같은 질문의 답이 그대로 검색될 수 있다.

- **기준:** 시스템은 질문 시점(`as_of`)에 존재한 정보만 볼 수 있어야 한다. 이 경계는 LLM이 아니라 Application이 강제한다.
- **이번 구현** (`app/services/knowledge.py`):
  - 스레드·댓글은 `created_at < as_of`인 것만 보인다.
  - 날짜 없는 문서는 `as_of` 이전의 **가장 최근 분기 버전**만 보인다.
  - 날짜 있는 changelog·blog는 `as_of` **전날까지** 발표된 것만 보인다(같은 날은 시각을 몰라 보수적으로 제외).
  - 평가 대상 스레드 자신은 검색에서 제외한다(`exclude_thread`). 안 그러면 질문을 검색해서 정답 답글을 그대로 읽는다.

### 3.3 표본 추출: 선택 편향 줄이기

- **기준:** 사람이 "좋아 보이는" Case를 고르면 Golden Set이 특정 유형으로 쏠린다. 무작위 순서를 정해 두고, 그 순서대로 판정해서 앞에서부터 채운다.
- **이번 사례:** 후보 227건을 `random.Random(11)`로 섞고 1번부터 검토해서 적격 30건이 모이면 멈췄다(55번째에서 도달). 시드를 기록했기 때문에 같은 순서를 재현할 수 있다.
- **결과 기록:** Case마다 `review_rank`(섞인 순서)를 남겼다. 나중에 "왜 이 Case가 들어갔나"를 순서와 판정 사유로 설명할 수 있다.
- **이후 변화:** 추가 검토에서 1건을 제외했고 다음 순번으로 보충하지 않아 29건이 됐다.

### 3.4 적격 판정: "답할 수 있는 문제"만

- **기준:** 질문 시점 지식 베이스에 정답 핵심 주장의 근거가 있어야 적격.
- **사전 측정:** 본 선정 전에 20건 표본으로 답변 가능성을 먼저 쟀다(`kb-answerability-v1`). 가능 5 / 일부 9 / 불가 6. 불가 중 3건이 문서 시점 문제였고, 분기별 문서 버전을 도입해서 2건을 해결했다. Golden Set을 만들기 전에 **데이터가 문제를 풀 수 있는 상태인지** 먼저 본 것이다.
- **제외 26건의 유형:**

| 제외 유형 | 건수 | 예 |
|---|---:|---|
| 질문 시점 근거 없음·부족 | 11 | 참조한 공지·Discussion이 질문 이후에 생김, 로드맵 근거 없음 |
| 지식이 아닌 운영 상태 | 9 | 운영 장애, 버그 수정·인정, 외부(OpenAI) 계정 한도, "새 릴리스로 업그레이드" |
| 일반 조언·외부 예시 | 3 | 제품 문서와 무관한 일반론 |
| 행동 요구 | 2 | "이슈를 만들어 달라", 기여 요청 |
| 사람이 정답을 검증할 수 없음 | 1 | 중국어 질문(검토자가 읽을 수 없음) |

- **배운 점:** 실제 지원 답변의 상당수는 지식 검색으로 풀 문제가 아니다. "장애 중입니다", "고쳤습니다", "이슈 열어 주세요"는 지식 베이스에 근거가 있을 수 없다. 이걸 섞으면 RAG 성능이 아니라 데이터 성격을 측정하게 된다.

### 3.5 주장 단위 분해

답변 전체를 하나의 정답으로 두면 "부분적으로 맞은 답"을 채점하기 어렵다. 그래서 답변을 검증 가능한 **주장(claim)** 단위로 쪼갰다.

```json
{
  "case_id": "discussion-7791",
  "created_at": "2025-07-10T03:30:27Z",
  "claims": [
    {
      "id": "C1",
      "text": "Python SDK v3는 self-hosted 플랫폼 버전 3.63.0 이상을 요구하므로 플랫폼을 업그레이드한다",
      "evidence": ["docs/sdk/python/sdk-v3"]
    }
  ],
  "unscored_parts": []
}
```

- 29건 중 5건이 주장 2개 이상, 나머지는 1개.
- **`unscored_parts`:** 정답에 있지만 질문 시점 근거가 없는 부분이다. 예를 들어 7876의 "새 observations 필터 PR을 통한 우회책"은 질문 이후 정보라 채점하지 않는다. 현재 4건에 있다.
- **사례 — 처음엔 채점에서 뺐다가 되돌린 경우:** 7791은 원래 "정확한 버전 숫자(>=3.63)"를 채점 제외로 뒀다. 추가 검토에서 질문 시점 문서에 그 숫자가 명시돼 있음을 확인하고 주장에 포함했다. 채점 제외 판단도 근거를 다시 보면 바뀐다.

### 3.6 근거 연결과 as_of 실재성 점검

주장마다 근거(문서 경로·스레드 번호)를 붙인 뒤, **눈으로 본 것이 아니라 실제 검색 함수로 다시 조회**해서 질문 시점에 존재했는지 확인했다. 30건 전체 점검에서 3곳을 고쳤다.

| Case | 발견한 문제 | 원인 | 조치 |
|---|---|---|---|
| 8924 | 근거 문서 `docs/observability/sdk/overview`가 질문 시점에 없음 | 답변 링크가 문서 개편 후 경로. 질문 시점 분기 버전에는 같은 페이지가 `docs/sdk/overview`로 있음 | 질문 시점 경로로 교체 |
| 7800 | `self-hosting/security/authentication-and-sso` 없음 | 같은 원인(경로 개편) | `self-hosting/authentication-and-sso`로 교체 |
| 7876 | 근거 스레드 #7857이 실제로는 근거가 아님 | 같은 사용자가 하루 전에 올린 **동일 질문**이고 질문 시점 답글 0개 | 근거에서 제거 |

- **배운 점 1 — 링크를 그대로 근거로 쓰면 안 된다.** 답변의 링크는 답변 작성 시점(또는 이후 수정 시점)의 사이트 구조다. 우리 스냅샷은 분기 단위라 해상도가 다르다.
- **배운 점 2 — 제목이 같은 스레드는 정답이 아니라 중복 질문일 수 있다.** 검색으로 근거를 붙이면 이런 것이 섞인다. "답글이 있는가", "제목이 같은가" 같은 기계적 점검이 효과적이었다.

### 3.7 채점 설계: 두 층

정답 30건 중 25건이 링크 위주 답변이었다. 링크 일치로 채점하면 경로가 바뀐 같은 문서, 다른 정당한 문서를 인용한 답이 모두 오답이 된다. 그래서 정답 판정과 근거 측정을 분리했다.

| 층 | 무엇을 보나 | 누가 | 용도 |
|---|---|---|---|
| 1층 정답 여부 | 주장 **내용**이 답변에 담겼나 (링크·표현 무관) | 사람 라벨 → 이후 LLM Judge | **정답 판정은 이 층만** |
| 2층 근거 재현율 | 주장별 근거 중 하나라도 찾았나. 조회 기준(LLM 컨텍스트에 들어옴)과 인용 기준(최종 답변 인용)을 모두 기록 | 자동 | 비교용 보조 지표 |
| 2층 인용 유효성 | 인용한 경로·번호가 지식 베이스에 실재하고 `as_of` 이전 공개인가 | 자동 | 지어낸 인용·미래 정보 탐지 |

- **사례 — 링크 안내 주장 병합:** 9517 등 4건은 "C1 기능 미지원 / C2 기능 요청 #4060을 안내한다"로 나뉘어 있었다. C2의 근거가 C1과 똑같아서, C2를 따로 채점하면 같은 내용을 두 번 세게 된다. C2를 C1에 합치고 링크는 근거 목록으로만 남겼다(주장 41 → 37).
- **조회 기준 vs 인용 기준을 둘 다 남기는 이유:** 둘의 차이가 "찾았지만 답에 안 씀"이다. 이걸 보면 실패가 검색 단계인지 생성 단계인지 나눌 수 있다.
- **근거 목록의 한계를 인정:** 근거 목록은 모든 출처를 다 담지 않는다. 그래서 근거 지표는 정답 판정에 쓰지 않는다.

### 3.8 사람 검토

- **역할 분리:** 초안(주장·근거 작성)은 Claude, 확정은 사용자. 상태를 `draft` → `confirmed`로 기록하고 `confirmed_by`를 남겼다.
- **사례 — 검토되지 않은 Case 발견:** 중국어 Case를 빼고 넣은 대체 Case(8924)가 사용자 검토 문서에 없었다. "확정했다"고 생각했지만 1건은 사람이 본 적이 없었던 것이다. 이처럼 **교체·수정 이후에도 검토 범위가 따라왔는지** 확인해야 한다.
- **추가 검토 범위:** 미검토 1건 + 채점 제외가 있는 6건 + 게시 후 답변이 수정된 1건(수정 전 원문을 알 수 없어 질문 시점 이후 정보가 섞였을 수 있음) = 8건. 결과 1건 제외(9675: 근거 문서에 주장 내용이 없음), 1건 수정(7791).

## 4. 이번에 실제로 겪은 함정 정리

1. **미래 정보 누출:** 현재 문서로 과거 질문을 풀면 안 된다 → `as_of` 범위를 Application이 강제.
2. **자기 자신 검색:** 평가 대상 스레드가 검색되면 정답을 그대로 읽는다 → `exclude_thread`.
3. **중복 질문을 근거로 착각:** 제목 같은 이전 스레드에 답이 없었다.
4. **링크 경로 버전 불일치:** 답변 링크는 개편 후 경로, 스냅샷은 개편 전 경로.
5. **링크 일치 채점:** 같은 내용을 다른 출처로 답하면 오답 처리된다 → 내용 기준 채점.
6. **이중 계산:** "링크를 안내한다"를 별도 주장으로 두면 같은 근거를 두 번 센다.
7. **검토 범위 누락:** 교체된 Case가 검토 문서에 반영되지 않았다.
8. **검색 엔진 특성 미확인:** PostgreSQL `websearch_to_tsquery`는 모든 단어를 요구(AND)해서, 질문 원문을 통째로 넣으면 거의 아무것도 안 나온다. 검색 상한을 잴 때 이를 고려해야 한다.

## 5. 이 Golden Set의 한계

면접이나 이력서에서 과장하지 않으려면 한계를 같이 알아야 한다.

- **규모가 작다.** 29건·주장 35개는 경향을 보기에는 충분하지만, 작은 차이를 통계적으로 단정하기 어렵다.
- **라벨러가 사실상 1명이다.** 초안은 LLM(Claude), 확정은 사용자 1명이다. 라벨러 간 일치도(inter-annotator agreement)는 측정하지 않았다.
- **초안 작성자가 LLM이다.** 주장 문장은 Claude가 답변을 요약해 쓴 것이다. 요약 과정에서 정답의 뉘앙스가 바뀌었을 수 있다(사람 검토로 일부 완화).
- **근거 목록이 망라적이지 않다.** 그래서 근거 지표는 보조 지표로만 쓴다.
- **스냅샷 해상도가 분기 단위다.** 실제 사이트에는 있었던 페이지가 스냅샷에는 아직 없을 수 있다(8924 사례).
- **단일 제품·단일 출처다.** Langfuse Discussion만 썼다. 다른 제품이나 티켓 형식으로 일반화할 수 있는지는 모른다.
- **아직 이 데이터로 실험을 돌리지 않았다.** Golden Set의 변별력(Workflow와 Agent를 구분하는가)은 아직 검증되지 않았다.

## 6. 재사용 체크리스트

새 Golden Set을 만들 때 이번 순서를 그대로 쓸 수 있다.

- [ ] 정답 권위가 있는 출처인가 (작성자 역할 확인)
- [ ] 질문 시점(`as_of`)을 정하고, 그 이후 정보를 Application에서 차단했는가
- [ ] 평가 대상 자신이 검색되지 않게 했는가
- [ ] 무작위 순서와 시드를 기록하고 그 순서대로 판정했는가
- [ ] 본 선정 전에 작은 표본으로 답변 가능성을 측정했는가
- [ ] 제외 사유를 Case마다 기록했는가
- [ ] 정답을 주장 단위로 쪼개고, 근거 없는 부분은 채점에서 분리했는가
- [ ] 근거를 실제 검색 함수로 다시 조회해 시점 실재성을 확인했는가
- [ ] 같은 근거를 두 번 세는 주장이 없는가
- [ ] 정답 판정(내용)과 근거 지표(자동)를 분리했는가
- [ ] 교체·수정한 Case까지 사람이 검토했는가
- [ ] 한계(규모, 라벨러 수, 근거 망라성)를 문서에 남겼는가

## 7. 이력서·면접에서 설명하는 방법

**실제로 한 일만** 쓴다. 아직 실험 결과가 없으므로 성능 수치는 쓰지 않는다.

이력서 문장 예시:

> 실제 공개 지원 데이터(Langfuse GitHub Discussion)로 RAG·Agent 비교용 Golden Set 구축. 메인테이너 답변 227건에서 시드 고정 무작위 순서로 55건을 검토해 29건·채점 주장 35개를 확정하고, 질문 시점(as_of) 이후 정보를 차단하는 검색 범위를 설계하고, 근거를 검색 함수로 재조회하는 시점 검증으로 근거 오류 3건(문서 경로 버전 불일치 2, 중복 질문 1)을 수정.

면접에서 나올 만한 질문과 답의 뼈대:

| 질문 | 답의 핵심 |
|---|---|
| 왜 직접 만든 문제가 아니라 실제 데이터인가 | 만든 사람이 정답을 알고 쓰면 문제가 쉬워진다. 실제 문의는 표현이 불완전하고 근거가 흩어져 있다 |
| 데이터 누출은 어떻게 막았나 | `as_of` 이전 문서·스레드만 보이게 Application에서 강제, 대상 스레드 자신은 제외, 근거를 검색 함수로 재조회해 시점 확인 |
| 왜 링크 일치로 채점하지 않았나 | 문서 경로가 개편으로 바뀌고 정당한 출처가 여러 개다. 정답은 내용으로, 근거는 보조 지표로 분리 |
| 선택 편향은? | 시드 고정 무작위 순서대로 판정, 제외 사유 전부 기록 |
| 이 Golden Set의 약점은? | 29건으로 작고 라벨러가 1명, 근거 목록이 망라적이지 않음, 단일 제품 |
